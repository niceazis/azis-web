# Initial customer validation plan

Status: planned. This is not a claim of current customers, pilots, interviews, or measured time savings.

## Target

Project managers and team leads at software teams of 5–30 people, beginning with release coordination involving design approval, implementation, and launch preparation.

## Small experiment

Recruit three target users who consent to a short evaluation. Ask each to bring five redacted or synthetic release updates that they are authorized to share. Do not use confidential company communications without authorization.

First have them identify follow-ups manually. Then have them review AZIS suggestions for the same updates. Record:

- Which proposed follow-ups they would actually send.
- Which useful follow-ups were missed.
- Whether any owner, deadline, or approval state was invented.
- Manual review time compared with assisted review time.
- Whether they want to use the tool on the next release.

## Proposed decision rules

These are experiment thresholds, not measured results.

- Continue if at least two of three users want another session and at least 70% of proposed follow-ups are judged useful.
- Require zero invented committed owners/deadlines and zero false execution claims in the pilot before expanding access.
- Record both misses and false alarms; a low-noise tool that misses all meaningful blockers is not successful.
- Add Slack or Teams integration only after repeated use shows that manual input is the main obstacle.
- If users find the drafts useful but blocker detection weak, focus the product on evidence-backed follow-up drafting while improving detection.

## Evidence publication

Publish only consented, anonymized results with actual sample sizes and limitations. Update the website's stage only when corresponding work and evaluation have occurred.
